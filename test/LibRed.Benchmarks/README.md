# LibRed.Benchmarks

BenchmarkDotNet harness measuring **LibRed's engine directly**. SQL goes into `QueryEngine`; nothing here goes
through EF Core or the ADO layer, because EF's per-query overhead is large enough to hide the thing being
measured (a slow test in the functional suites is usually not a slow query — see the repo notes on that).

```powershell
dotnet run --project test\LibRed.Benchmarks -c Release                          # menu
dotnet run --project test\LibRed.Benchmarks -c Release -- --validate            # sanity-check the corpus
dotnet run --project test\LibRed.Benchmarks -c Release -- --filter "*join.*"    # one family of shapes
dotnet run --project test\LibRed.Benchmarks -c Release -- --filter "*Pipeline*" # parse/plan/execute split
dotnet run --project test\LibRed.Benchmarks -c Release -- --scale 10000,200000  # growth, not a constant
dotnet run --project test\LibRed.Benchmarks -c Release -- --long                # publishable iteration counts
dotnet run --project test\LibRed.Benchmarks -c Release -- --filter "*Ace*"      # head-to-head vs ACE OLE DB
```

`-c Release` is not optional — BenchmarkDotNet refuses to run an unoptimised build.

## The suites

| Suite | What it answers |
| --- | --- |
| `SyntheticQueryBenchmarks` | End-to-end cost of every read in the corpus, per scale factor. The broad regression net. |
| `NorthwindQueryBenchmarks` | The same, over real-world shapes: text keys, a table name with a space, skewed groups. |
| `PipelineBenchmarks` | Parse vs bind+plan vs execute vs end-to-end, on a representative spread. Attribution. |
| `StorageBenchmarks` | Cursors and index seeks with no SQL above them — the floor everything else sits on. |
| `WriteBenchmarks` | INSERT/UPDATE/DELETE throughput: SQL autocommit, SQL in a transaction, and raw storage. |
| `DdlBenchmarks` | Creating a database from nothing, creating tables, back-filling an index. |
| `CatalogBenchmarks` | Open + catalog decode: the fixed price every connection pays. |
| `AceComparisonBenchmarks` | Identical SQL and file against ACE OLE DB. ACE is the baseline; ratio < 1 is a win. |

## The corpus

`SqlCorpus` is the single list of benchmarked statements; every suite draws from it, so adding a benchmark is
adding a line. Cases are named `category.what_it_does`, which is also what `--filter` matches.

`Corpus` generates the synthetic database — three tables at a caller-chosen scale factor, with known
cardinalities:

| Column | Shape |
| --- | --- |
| `Bench.Id` | Unique, primary key. Point-lookup target. |
| `Bench.K` | 1,000 distinct values, indexed. Low-cardinality grouping and duplicate-key seeks. |
| `Bench.Bucket` | 8 values, varying *within* a `K` group — the second column of the composite index. |
| `Bench.G` | scale/4 distinct values, **unindexed**. High-cardinality grouping, hash-join key. |
| `Bench.Label` | 5,000 distinct values, indexed text. |
| `Bench.Note` | Unindexed text, null in one row of eight, needle `qx` in one of twenty. |
| `BenchChild` | 2× `Bench` rows, two children per parent: joins with real fan-out. |
| `BenchSmall` | 100 rows: the small side of a hash join. |

It is generated by LibRed itself, so it needs no Access engine and builds on Linux and macOS. It is cached
under the system temp directory keyed by scale and schema version, and read-only suites open it in place —
a large scale factor costs nothing per run after the first.

## Rules for adding a benchmark

1. **Drain the result.** `ResultSet.Rows` is lazy; returning it measures plan construction and reports a
   million-row scan as a few hundred nanoseconds. Return `Consume.Drain(...)`.
2. **Run `--validate` afterwards.** It runs every case once and prints the row count. A case that returns zero
   rows is worse than one that throws — it produces a fast, meaningless number. That is exactly how
   `predicate.composite_eq` was born broken: `K` and `G` shared a period, so `K = 500 AND G = 7` matched nothing.
3. **Keep it deterministic.** No `Now()`, no unseeded randomness — two runs of one commit must be comparable.
4. **Writes need isolation.** A write benchmark gets a fresh copy per iteration and `[InvocationCount(1, 1)]`;
   without that the second iteration measures a table the first one already grew.
5. **Mark what ACE cannot run.** `RunsOnAce: false` for window functions, `INFORMATION_SCHEMA`, and anything
   else in LibRed's capability-gap list. The head-to-head skips those instead of reporting an ACE failure.

## Reading the results

Two numbers together usually say more than either alone:

- `PipelineBenchmarks.Parse` against `EndToEnd` — how much of a small query is ANTLR. On a point lookup it is
  most of it, which is what would make a prepared-statement cache worth building.
- `StorageBenchmarks.FullScan` against `SyntheticQueryBenchmarks[scan.star]` — the price of the SQL pipeline
  over the same rows. If they are close, planner work will not help.
- `WriteBenchmarks.InsertStorage` against `InsertSqlAutocommit` — the same question for writes.
- `DuplicateKeySeek` against `RangeSeek` — B-tree descent separated from traversal.

Reports are exported to `Results/` as GitHub markdown and CSV. Nothing there is tracked by default; `git add -f`
a run you want to keep for comparison.

## Caveats

- The in-process toolchain is used deliberately: BenchmarkDotNet's default toolchain builds a throwaway project
  per benchmark and does not yet recognise this repo's preview `net11.0`. The cost is slightly weaker isolation
  between benchmarks.
- `CatalogBenchmarks.OpenAndLoadCatalog` is a cold *decode*, not cold I/O — the OS file cache stays warm and no
  portable benchmark can change that.
- The ACE comparison needs a matching-bitness Access driver and is prone to crashing the host process under
  sustained load; run it on its own.
